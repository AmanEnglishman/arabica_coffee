# Техническое задание

## Проект

**Arabica Coffee** - backend-система для кофейни с REST API, админ-панелью, каталогом меню, корзиной, заказами, бонусной программой, акциями и новостями.

Система предназначена для клиентского мобильного или web-приложения, сотрудников кафе, курьеров и администраторов.

## Цели проекта

1. Автоматизировать оформление заказов в кофейне.
2. Предоставить клиентам доступ к меню, корзине, истории заказов, акциям, новостям и бонусной программе.
3. Обеспечить сотрудникам кафе инструменты для обработки заказов.
4. Обеспечить курьерам инструменты для доставки заказов и работы с бонусной программой.
5. Дать администратору возможность управлять контентом, меню, пользователями, филиалами и заказами.

## Роли пользователей

### Гость

Пользователь без авторизации.

Возможности:
- просмотр публичных разделов API, если endpoint не требует авторизации;
- отправка кода подтверждения на номер телефона;
- подтверждение номера телефона и получение JWT-токенов.

### Клиент

Авторизованный пользователь кофейни.

Возможности:
- просмотр и редактирование профиля;
- просмотр меню;
- поиск товаров;
- просмотр карточки товара;
- добавление товаров и опций в корзину;
- редактирование и удаление позиций корзины;
- создание заказа из корзины;
- просмотр списка и деталей своих заказов;
- повторение ранее созданного заказа;
- просмотр активных заказов;
- просмотр бонусных баллов, QR-кода и количества чашек кофе;
- просмотр новостей и акций.

### Сотрудник кафе

Пользователь, привязанный к конкретному кафе через `CafeMembership` с ролью `staff`.

Возможности:
- просмотр заказов только своего филиала;
- фильтрация заказов по статусу;
- перевод заказа из статуса `accepted` в `ready`;
- назначение курьера на заказ доставки;
- завершение заказа самовывоза.

### Курьер

Пользователь с ролью курьера и признаком `is_courier`.

Возможности:
- просмотр назначенных заказов доставки;
- подтверждение доставки заказа;
- сканирование QR-кода клиента;
- начисление бонусных баллов клиенту;
- добавление чашки кофе в программу лояльности.

### Администратор

Пользователь с доступом к Django Admin.

Возможности:
- управление пользователями;
- управление категориями, подкатегориями, товарами и опциями;
- управление кафе и привязками сотрудников;
- управление заказами;
- управление новостями и акциями;
- массовый импорт меню через API;
- просмотр и корректировка данных системы.

## Функциональные требования

### 1. Авторизация и пользователи

Система должна поддерживать авторизацию по номеру телефона.

Требования:
- пользователь вводит номер телефона;
- система отправляет код подтверждения через Twilio;
- пользователь подтверждает код;
- при успешной проверке система создает пользователя, если он еще не существует;
- система помечает номер телефона как подтвержденный;
- система возвращает JWT `access` и `refresh` токены;
- авторизованный пользователь может получить и обновить свой профиль.

Профиль пользователя должен содержать:
- номер телефона;
- имя;
- фамилию;
- пол;
- дату рождения;
- аватар;
- QR-код;
- бонусные баллы;
- количество чашек кофе;
- признаки активности, сотрудника и курьера.

### 2. Меню

Система должна предоставлять каталог товаров кофейни.

Структура меню:
- категория;
- подкатегория;
- товар;
- типы опций;
- значения опций.

Товар должен содержать:
- название;
- цену;
- изображение;
- описание;
- процент начисления бонусов;
- подкатегорию;
- признак наличия опций;
- признак активности.

Опция должна содержать:
- тип опции, например объем или молоко;
- значение опции;
- дополнительную стоимость.

Требования:
- получение полного меню с категориями и подкатегориями;
- получение детальной информации о товаре;
- поиск товаров по названию без учета регистра;
- поддержка кэширования меню;
- массовый импорт категорий, подкатегорий, товаров и опций для администратора.

### 3. Корзина

Система должна хранить корзину отдельно для каждого пользователя.

Требования:
- у пользователя может быть одна активная корзина;
- пользователь может получить текущую корзину;
- пользователь может добавить товар в корзину;
- пользователь может выбрать опции товара;
- пользователь может указать комментарий к позиции;
- пользователь может изменить количество и комментарий позиции;
- пользователь может удалить позицию из корзины;
- если при удалении количество больше одного, система уменьшает количество на 1;
- итоговая стоимость позиции должна учитывать базовую цену товара, стоимость выбранных опций и количество;
- итоговая стоимость корзины должна считаться как сумма всех позиций;
- данные корзины могут кэшироваться и должны инвалидироваться при изменениях.

### 4. Заказы

Система должна создавать заказ на основе текущей корзины пользователя.

Требования:
- заказ создается только авторизованным пользователем;
- заказ создается только при непустой корзине;
- пользователь должен выбрать активное кафе;
- заказ может быть оформлен как доставка или самовывоз;
- для доставки должен поддерживаться адрес;
- должно поддерживаться желаемое время доставки;
- после создания заказа позиции корзины переносятся в заказ;
- выбранные опции товара сохраняются в заказе;
- итоговая сумма заказа фиксируется на момент создания;
- после создания заказа корзина очищается;
- пользователю начисляются бонусные баллы на основе `bonus_percent` товаров;
- пользователь может просматривать только свои заказы;
- пользователь может получить список своих заказов с пагинацией;
- пользователь может получить детали своего заказа;
- пользователь может повторить заказ, добавив его товары в корзину.

Статусы заказа:
- `accepted` - заказ принят;
- `ready` - заказ готов;
- `on_the_way` - курьер в пути;
- `delivered` - заказ доставлен или выдан.

Переходы статусов:
- сотрудник кафе переводит `accepted` в `ready`;
- для доставки сотрудник кафе назначает курьера и переводит `ready` в `on_the_way`;
- курьер переводит `on_the_way` в `delivered`;
- для самовывоза сотрудник кафе переводит `ready` в `delivered`.

### 5. Кабинет кафе

Система должна ограничивать сотрудника кафе заказами только его филиала.

Требования:
- сотрудник видит список заказов своего кафе;
- сотрудник может фильтровать заказы по статусу;
- сотрудник не должен видеть и изменять заказы других кафе;
- сотрудник может отметить заказ готовым;
- сотрудник может назначить курьера своего кафе на заказ доставки;
- сотрудник может завершить заказ самовывоза.

### 6. Кабинет курьера

Система должна предоставлять курьеру только назначенные ему заказы.

Требования:
- курьер видит свои заказы;
- по умолчанию отображаются заказы в статусе `on_the_way`;
- курьер может фильтровать заказы по статусу;
- курьер может подтвердить доставку заказа;
- курьер не должен видеть заказы других курьеров.

### 7. Бонусная программа

Система должна поддерживать бонусные баллы и накопление чашек кофе.

Требования:
- у каждого пользователя есть уникальный QR-код;
- курьер может сканировать QR-код клиента;
- по QR-коду система возвращает данные клиента, баллы и количество чашек;
- курьер может начислить клиенту бонусные баллы;
- курьер может добавить клиенту чашку кофе;
- после накопления 6 чашек счетчик сбрасывается, а клиент получает бесплатную чашку;
- клиент должен иметь возможность видеть информацию о бонусной программе.

### 8. Новости

Система должна предоставлять список новостей и детальную страницу новости.

Новость должна содержать:
- заголовок;
- изображение;
- краткое описание;
- полный текст;
- дату публикации;
- признак активности;
- дату создания.

Требования:
- отображать активные новости;
- сортировать новости по дате публикации в обратном порядке;
- поддерживать пагинацию;
- предоставлять детальную информацию по `id`.

### 9. Акции

Система должна предоставлять список акций и детальную страницу акции.

Акция должна содержать:
- заголовок;
- изображение;
- краткое описание;
- полный текст;
- дату публикации;
- признак активности;
- дату создания.

Требования:
- отображать активные акции;
- сортировать акции по дате публикации в обратном порядке;
- поддерживать пагинацию;
- предоставлять детальную информацию по `id`.

### 10. Администрирование

Система должна использовать Django Admin для управления основными сущностями.

Требования:
- доступ к админ-панели должен быть только у пользователей с правами администратора;
- администратор должен управлять меню, заказами, пользователями, кафе, новостями и акциями;
- интерфейс админки должен поддерживать загрузку изображений;
- массовый импорт меню должен быть доступен только администратору.

## API

Базовый префикс API: `/api/v1/`.

Основные группы endpoint-ов:

| Раздел | Endpoint |
| --- | --- |
| Авторизация | `/api/v1/auth/send-code/` |
| Авторизация | `/api/v1/auth/verify-code/` |
| Профиль | `/api/v1/auth/me/` |
| JWT | `/api/v1/auth/token/` |
| JWT refresh | `/api/v1/auth/token/refresh/` |
| JWT status | `/api/v1/auth/token/status/` |
| Меню | `/api/v1/menu/` |
| Детали товара | `/api/v1/menu/<id>/` |
| Поиск товара | `/api/v1/menu/search/?search=<text>` |
| Массовый импорт меню | `/api/v1/menu/bulk-import/` |
| Корзина | `/api/v1/cart/cart/` |
| Добавление в корзину | `/api/v1/cart/cart/item/` |
| Обновление позиции | `/api/v1/cart/cart/item/<id>/` |
| Удаление позиции | `/api/v1/cart/cart/item/<id>/delete/` |
| Создание заказа | `/api/v1/orders/create/` |
| Заказы пользователя | `/api/v1/orders/` |
| Детали заказа | `/api/v1/orders/<id>/` |
| Повтор заказа | `/api/v1/orders/<id>/reorder/` |
| Активные заказы | `/api/v1/orders/active/` |
| Заказы кафе | `/api/v1/orders/cafe/orders/` |
| Заказ готов | `/api/v1/orders/cafe/orders/<id>/mark-ready/` |
| Назначение курьера | `/api/v1/orders/cafe/orders/<id>/assign-courier/` |
| Выдача самовывоза | `/api/v1/orders/cafe/orders/<id>/mark-delivered/` |
| Заказы курьера | `/api/v1/orders/courier/orders/` |
| Доставка завершена | `/api/v1/orders/courier/orders/<id>/deliver/` |
| QR-сканирование | `/api/v1/bonus/qr-scan` |
| Начисление баллов | `/api/v1/bonus/add-points/` |
| Добавление чашки | `/api/v1/bonus/add-coffee-cup/` |
| Информация о бонусах | `/api/v1/bonus/` |
| Новости | `/api/v1/news/` |
| Детали новости | `/api/v1/news/<id>/` |
| Акции | `/api/v1/promotions/` |
| Детали акции | `/api/v1/promotions/<id>/` |
| OpenAPI schema | `/api/v1/schema` |
| Swagger UI | `/api/v1/swagger/` |
| Redoc | `/api/v1/redoc/` |

Ответы API должны быть в формате JSON.

Ошибки должны возвращаться в едином формате через общий механизм `api_error`, где это предусмотрено реализацией.

## Нефункциональные требования

### Безопасность

- Использовать JWT-аутентификацию для защищенных endpoint-ов.
- Не хранить секретные ключи, пароли, токены Twilio и данные базы в репозитории.
- Ограничивать доступ к действиям по ролям.
- Клиент не должен иметь доступ к заказам других пользователей.
- Сотрудник кафе не должен иметь доступ к заказам других филиалов.
- Курьер не должен иметь доступ к заказам других курьеров.
- Административные операции должны быть доступны только администраторам.

### Производительность

- Кэшировать меню, карточки товаров, поиск и корзину там, где это предусмотрено.
- Использовать пагинацию для списков заказов, новостей и акций.
- Использовать индексы для часто фильтруемых полей, например `is_active` и `published_at`.

### Надежность

- Создание заказа должно выполняться в транзакции.
- Переходы статусов заказа должны проверяться на корректность.
- При недоступности Twilio система должна возвращать понятную ошибку.
- При повторе заказа недоступные товары должны пропускаться с предупреждением.

### Документация

- API должно быть доступно в Swagger UI и Redoc.
- Документация должна описывать группы API, входные данные и возможные ответы.
- Для CI/CD должен поддерживаться отдельный документ настройки.

## Развертывание

Проект должен поддерживать запуск через Docker Compose.

Состав окружения:
- Django application;
- PostgreSQL;
- Redis;
- Nginx.

Production-запуск должен использовать:
- `DEBUG=False`;
- корректный `SECRET_KEY`;
- переменные окружения для базы данных, Redis и Twilio;
- сбор статических файлов;
- миграции базы данных;
- Docker-образ приложения;
- CI/CD pipeline для проверки и деплоя.

## CI/CD

CI pipeline должен:
- запускаться при push и pull request;
- устанавливать зависимости;
- поднимать PostgreSQL и Redis для тестов;
- проверять форматирование;
- запускать линтер;
- запускать тесты;
- формировать отчет о покрытии.

CD pipeline должен:
- запускаться при push в `main` или создании release-тега;
- собирать Docker-образ;
- публиковать образ в registry;
- выполнять деплой на сервер через SSH.

## Критерии приемки

Проект считается готовым, если:

1. Пользователь может авторизоваться по телефону и получить JWT-токены.
2. Пользователь может просматривать меню, искать товары и открывать карточку товара.
3. Пользователь может собрать корзину с товарами, опциями и комментариями.
4. Пользователь может создать заказ из корзины.
5. После создания заказа корзина очищается, а заказ сохраняет товары, опции и итоговую сумму.
6. Пользователь может видеть историю и детали своих заказов.
7. Пользователь может повторить заказ.
8. Сотрудник кафе видит только заказы своего филиала и может менять их статусы в допустимом порядке.
9. Курьер видит только свои заказы и может отметить доставку.
10. Курьер может сканировать QR-код клиента и начислять бонусы.
11. Новости и акции доступны списком и детально.
12. Администратор может управлять данными через Django Admin.
13. Swagger и Redoc доступны по указанным URL.
14. Проект запускается через Docker Compose.
15. Тесты проекта проходят успешно.
16. CI/CD настроен и выполняет проверку проекта.

## Ограничения и допущения

- Frontend-приложение не входит в текущий backend-проект.
- Оплата заказа в текущем проекте не реализована и может быть добавлена отдельным модулем.
- Геолокация курьера и расчет стоимости доставки не реализованы.
- Push-уведомления и уведомления о статусах заказа не реализованы.
- Интеграция с кассовой системой не реализована.
- Управление правами сотрудников выполняется через данные пользователя и `CafeMembership`.
